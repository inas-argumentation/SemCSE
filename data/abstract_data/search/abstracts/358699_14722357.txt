The Many Views of Quality and How it compares with my Experience
A recent column in an online magazine stimulated about twice the usual number of reader comments. The column was titled "Quality: What a Fuzzy Term" by Robert L Glass (www.stickyminds.com) and has subsequently resulted in a follow up column, "Revisiting the Definition of Software Quality" Why all the furore about the definition of software quality? Is it really such a big issue? It does seem that a lot of software professionals are still grappling with the concept. I think Robert Glass is on the right wavelength when he defines quality as "a bunch of "ilities" such as reliability, usability, understandability, modifiability, testability and portability. Robert's bunch of "ilities" is defined in ISO 9126 in terms of quality characteristics, sub characteristics and metrics. The concept is taken further in ISO 14598, Evaluation of software product. I agree with readers who suggest identifying the "ilities" is the same as defining user requirements (for all classes of user, over the expected product lifetime. The above standards provide an organised approach and sample metrics. My own view is that Robert gets it wrong in the following areas: 1. Achieving cost and schedule targets are not normally part of the definition of quality. The more common view is that there is a 4 way trade off between quality, cost, schedule and functionality. Established estimating techniques help us to identify realistic trade offs. These techniques should be part of our development methodology. 2. The major thrust of the 80s was about improving productivity via process, not via people. This included automating the processes, creating better development tools and using new methods, e.g. object oriented development. 3. Software quality is only a "fuzzy" concept if considered in isolation from its normal context, which is the software engineering discipline. For any software development project, the project plan should contain (or reference) a quality plan. The quality plan identifies the phase deliverables (plans, requirements documents, design documents, program code etc. The quality plan identifies the standards/procedures/ guidelines etc to be used, and also describes the reviews, inspections, walkthroughs, audits and the like which will provide verification and validation.
